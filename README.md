# Cinema API · PostgreSQL

Серверна частина кінотеатру: фільми, зали, розклад сеансів і бронювання місць. Побудована на NestJS, дані зберігаються в PostgreSQL через TypeORM, схема бази створюється міграціями.

Це продовження домашнього завдання №1: зовнішня поведінка маршрутів лишилася тією самою, масиви в сервісах замінено таблицями. Нове:

- `GET /showings` віддає сторінку `{ items, total, page, limit }` з параметрами `page`, `limit`, `sort`;
- бронювання кількох місць записується в одній транзакції;
- одне місце на одному сеансі не можна продати двічі навіть при одночасних запитах: це гарантує унікальний індекс бази;
- усі помилки мають єдину структуру `{ statusCode, message, error, path, timestamp }`.

## Встановлення

Потрібні Node.js 22.12 або новіший і Docker.

```bash
npm install
```

## Змінні середовища

Створіть файл `.env` у корені проєкту, наприклад скопіюйте зразок командою `cp .env.example .env`:

```dotenv
PORT=3000

DB_HOST=localhost
DB_PORT=5433
DB_USER=cinema
DB_PASSWORD=cinema
DB_NAME=cinema
```

| Змінна        | Опис                         | Обов'язкова       |
| ------------- | ---------------------------- | ----------------- |
| `PORT`        | Порт, на якому слухає сервер | ні, типово `3000` |
| `DB_HOST`     | Хост PostgreSQL              | так               |
| `DB_PORT`     | Порт PostgreSQL на хості     | так               |
| `DB_USER`     | Користувач бази              | так               |
| `DB_PASSWORD` | Пароль користувача           | так               |
| `DB_NAME`     | Назва бази                   | так               |

Змінні проходять валідацію класом `EnvironmentVariables` ([src/config/env.validation.ts](src/config/env.validation.ts)): якщо параметрів підключення бракує, застосунок не стартує. Docker Compose бере ті самі значення з `.env`. Порт `5433` обрано, щоб не конфліктувати з локально встановленим PostgreSQL на `5432`.

## Запуск

Підняти базу даних через Docker Compose:

```bash
docker compose up -d
```

Застосувати міграції:

```bash
npm run migration:run
```

Заповнити базу тестовими даними (2 фільми, 2 зали, 4 сеанси в різні дати, 1 бронювання). Повторний запуск не створює дублікатів:

```bash
npm run seed
```

Запустити застосунок у режимі розробки:

```bash
npm run start:dev
```

Swagger доступний на [http://localhost:3000/docs](http://localhost:3000/docs).

## Міграції

| Команда                                                      | Що робить                                   |
| ------------------------------------------------------------ | ------------------------------------------- |
| `npm run migration:run`                                      | застосовує всі нові міграції                |
| `npm run migration:revert`                                   | відкочує останню міграцію                   |
| `npm run migration:show`                                     | показує, які міграції застосовано           |
| `npm run migration:generate -- src/database/migrations/Name` | генерує міграцію з різниці сутностей і бази |

Файл джерела даних для CLI TypeORM: [src/data-source.ts](src/data-source.ts). Міграції лежать у [src/database/migrations](src/database/migrations). Застосовану міграцію не редагують: зміна схеми означає нову міграцію.

## Перевірка роботи

Файл [requests.http](requests.http) містить запит до кожного маршруту і на кожну описану помилку. Відкрийте його у VS Code з розширенням REST Client і виконуйте запити згори вниз: ідентифікатори підставляються зі змінних, очікуваний код відповіді вказаний у заголовку запиту.

Автоматичні тести (потрібна запущена база; тести створюють окрему базу `cinema_test` і не чіпають робочих даних):

```bash
npm run test:e2e
```

## Схема бази даних

```
films ──┐                ┌── halls
        │ 1           1  │
        └──< showings >──┘          film_id, hall_id: ON DELETE RESTRICT
                │ 1
                ├──< bookings              showing_id: ON DELETE RESTRICT
                │        │ 1
                │        └──< booking_seats   booking_id: ON DELETE CASCADE
                └───────────<                 showing_id: ON DELETE RESTRICT

UNIQUE (booking_seats.showing_id, row, seat)
```

- `booking_seats.showing_id` дублює сеанс бронювання навмисно: унікальний індекс будується по колонках однієї таблиці, тож саме база не дає продати місце двічі.
- Перелік місць залу в базі не зберігається, сервіс обчислює його з `rows` і `seats_per_row`.

## Структура

```
src/
├── common/      спільні декоратори, pipe і глобальний фільтр винятків
├── config/      валідація змінних середовища
├── database/    налаштування підключення, міграції, коди помилок PostgreSQL
├── films/       операції з фільмами
├── halls/       операції із залами, обчислення переліку місць
├── showings/    операції із сеансами, розклад з посторінковою видачею
├── bookings/    бронювання та зайнятість місць на сеансі
├── data-source.ts  джерело даних для CLI TypeORM
└── seed.ts      заповнення бази тестовими даними
```

Залежності між модулями йдуть в один бік: `bookings → showings → films, halls`.

## Домовленості

- `startsAt` зберігається в `timestamptz` і повертається в UTC, тому `2030-06-15T18:00:00+03:00` у відповіді стане `2030-06-15T15:00:00.000Z`. Фільтр `date` теж рахує добу за UTC.
- `GET /showings`: `page` від 1 (типово 1), `limit` від 1 до 100 (типово 20), `sort` — `asc` або `desc` за часом початку (типово `asc`). Сеанси з однаковим часом упорядковані за `id`. Фільтрація, сортування та обрізання сторінки виконуються в SQL-запиті.
- Видалити фільм чи зал, на який посилається сеанс, не можна: відповідь `409`. Перевірку робить зовнішній ключ `ON DELETE RESTRICT`.
- Якщо хоча б одне місце в запиті на бронювання зайняте, відповідь `409` і в базі не лишається ні бронювання, ні його місць. Текст помилки бази у відповідь не потрапляє.
- Неправильно сформований `:id` дає 404, як і неіснуючий, бо запису з таким id немає.
- Поля, яких немає в DTO, мовчки відкидаються, запит через них не падає.
- Зал обмежений 1000 рядами і 1000 місцями в ряду, а ціна квитка 100 000 000 копійок. Рік випуску фільму не може бути раніше за 1888.
